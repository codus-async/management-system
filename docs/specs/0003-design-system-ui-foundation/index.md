# 0003. Design system and UI foundation

**Date**: 2026-10-12
**Status**: In Progress

## Summary

Every screen in this product should look and behave like one thing. This decision sets the visual language (type, color, spacing), installs a first set of accessible base components, and stands up the app frame (the shell every page sits inside), so later features build screens instead of rebuilding UI plumbing. The look is quiet and professional: warm ivory surfaces, ink text, a terracotta accent, warm tinted greys, Newsreader serif headings over Inter interface text, light and dark themes, and a left sidebar with a top bar. The accessibility bar is WCAG 2.2 AA for the parts this feature owns: text contrast, interactive component boundaries, full keyboard operability with a visible focus indicator, focus not obscured by the sticky top bar, and adequate target size on icon only controls. Other AA criteria that need real product screens (form error association at scale, authentication) arrive with their features. A named design skill now also governs how new UI gets made, so the process is as settled as the tokens.

This spec was revised after the first build shipped and the result read as a wireframe. The cause was an over strict reading of the contrast rule, which forced every card edge and divider to a heavy grey. The revision splits interactive boundaries (which the standard does constrain) from decorative dividers (which it does not), adds a real surface ladder so cards separate by lightness rather than by a line, and gives hover and selection surfaces their own values so they are visible at all.

It was revised again after the engineer replaced the cool blue direction with a warm palette named Ember: ivory surfaces, ink text, a terracotta accent, and serif headings. The design record now describes that palette, and the handful of tokens that stopped meeting the bars were retuned. The accessibility bars themselves did not move.

## Requirements

**User stories**:
- As the PA, I want every screen to look and behave the same so that I can work without relearning the interface each time I switch sections.
- As a developer on a later feature, I want tokens, base components, and the app shell ready so that I build product screens, not UI plumbing.
- As the CEO, I want a calm, readable interface that works from the keyboard and in dark mode so that I can check the briefing anywhere.

**Acceptance criteria** (the contract, each criterion is IDed and independently checkable):
- **AC-1**: `client/design.md` exists and documents the type scale, color tokens (light and dark, including the per theme accent), spacing scale, and the installed component inventory with short usage notes, matching the real tokens and components in the code. The token tables are generated from `globals.css` (a small script or documented copy step), not hand typed, so they cannot silently drift.
- **AC-2**: shadcn is initialized in the `new-york` style (or whatever style name the current CLI ships for that look; the build confirms the name at install time) with the zinc base palette; all theme values live as CSS variables wired through Tailwind 4 `@theme`; application code uses semantic token utilities (for example `bg-background`, `text-muted-foreground`) and no raw color utilities (for example `bg-zinc-100`).
- **AC-3**: Inter is loaded with `next/font/google` and is the UI sans typeface; Newsreader is loaded the same way and its CSS variable is exposed as `--font-newsreader`, which `globals.css` resolves through `--font-heading` so h1 to h3 render in the serif; Geist Sans is removed from the layout; Geist Mono remains available for code snippets; the type scale tokens, defined in `globals.css` in the first build step, are the only font sizes used in shell and demo screens, and `design.md` documents those tokens after they exist.
- **AC-4**: The Slice 1 component set is installed: button, input, select, textarea, checkbox, label, card, dialog, dropdown menu, table, badge, tabs, a toast or sonner notification (whichever the current shadcn registry ships as supported), and skeleton. Every interactive component is operable from the keyboard alone, shows a visible focus indicator that is not drawn at partial opacity, meets the 24 by 24 CSS pixel minimum target size (WCAG 2.5.8) including icon only buttons, and nothing important is obscured when focus lands under the sticky top bar (WCAG 2.4.11).
- **AC-5**: An app shell renders with a left sidebar (section navigation) and a top bar (search slot, theme toggle, user menu placeholder); navigation items come from a single typed config module with an optional `disabled` flag, seeded with the planned sections, and items not yet built render as disabled rather than as links to missing pages; on small screens the sidebar collapses into an accessible drawer.
- **AC-6**: Light, dark, and system themes all render correctly; the top bar offers a three way toggle; system preference is respected on first load and when system is selected; the choice persists across reloads; the toggle avoids a hydration mismatch by rendering a stable placeholder until mounted.
- **AC-7**: A client form is wired with React Hook Form and Zod (client Zod is major version 4, matching the backend, with `@hookform/resolvers` at a version that supports Zod 4) using the form primitive the current shadcn registry ships (the Form component or its Field based successor; the build confirms the name at install time); a demo form shows labels, inline validation errors, and focus moving to the first field with an error on failed submit.
- **AC-8**: Shared loading, empty, and error state patterns ship with the foundation: the skeleton component for loading, the shadcn Empty component (or its current registry equivalent) for empty lists, and a documented error state pattern; a demo view exercises all three.
- **AC-9**: Text and interface contrast meets WCAG 2.2 AA in both themes, correctly scoped: at least 4.5 to 1 for normal text and at least 3 to 1 for large text. The 3 to 1 non text bar applies to the visual boundaries of **interactive** components only, which in this token layer means the `--input`, `--ring`, and `--sidebar-border` tokens plus any token used as a control outline. Decorative and structural borders (card edges, table dividers, section separators, which map to `--border`) are **not** held to 3 to 1; they are set to a hairline weight and the contrast gate skips them. The automated accessibility check verifies the interactive set and fails the build on a regression there.
- **AC-10**: `client/` passes lint, format, and typecheck with the new code.
- **AC-11**: Light mode carries a real surface ladder. `--background`, `--sidebar`, `--card`, and `--popover` are four distinct lightness values in ascending order, so a card separates from the page by its own surface and does not depend on its border to read as a card. Dark mode carries the same ladder at its own values.
- **AC-12**: Hover and selection surfaces are visibly distinct. `--accent` carries a faint tint of the primary hue so a hovered dropdown row or a selected nav item is legible as hovered or selected. `--secondary` and `--muted` are distinct neutral values, not the same value under three names, so a secondary button and a muted panel do not look identical.
- **AC-13**: Elevation differs by theme. Light mode uses shadows: a soft shadow under cards, a stronger one under dialogs and dropdowns. Dark mode keeps shadows near zero and relies on the surface ladder, because a dark shadow on a dark surface reads as a smudge rather than as depth.
- **AC-14**: Neutrals are warm tinted rather than pure grey. Every neutral token in the surface ladder and the emphasis set (`--background`, `--foreground`, `--card`, `--sidebar`, `--muted`, `--secondary`, `--border`) carries chroma above zero at a hue between 80 and 115, the warm band the Ember palette sits in, so the greys read as a considered scale rather than as printer grey. The primary accent is terracotta inside that same warm band, so the accent and the neutrals sit together instead of the accent looking dropped in.
- **AC-15**: The way new UI is designed is written down and reachable. The `frontend-design` skill is vendored into the repo at `.agents/skills/frontend-design/` beside its `LICENSE.txt`, root `AGENTS.md` lists it under `## Agent skills` using that same relative path, and the path resolves to a real `SKILL.md`. The skill governs the design process (grounding the work in the subject, planning and reviewing before coding, restraint, and writing interface copy); it does not override the Ember palette, which this spec pins.

## Decision

**Chosen option**: Option 1: Tokens, components, and app shell, with the palette from Option 6

Build the foundation as one Tracer Bullet (a thin real path through every layer first): theme tokens live and one page renders inside the shell with dark mode working, then the component set, the full shell, states and forms, and the design.md pass thicken it.

**Implementation skills**: `frontend-design` (`anthropics/skills`, `.agents/skills/frontend-design/`) · `shadcn` (`shadcn-ui/ui`, `.agents/skills/shadcn/`) · `tailwind-v4-shadcn` (`secondsky/claude-skills`, `.agents/skills/tailwind-v4-shadcn/`) · `tailwind-design-system` (`wshobson/agents`, `.agents/skills/tailwind-design-system/`) · `react-hook-form` (`pproenca/dot-skills`, `.agents/skills/react-hook-form/`) · `zod` (`pproenca/dot-skills`, `.agents/skills/zod/`) · `suggest-lucide-icons` (`nweii/agent-stuff`, `.agents/skills/suggest-lucide-icons/`)

Settled implementation details (each is a call made with the full design context; the runner up is named so an override is easy):

- **Icons**: `lucide-react`. It is shadcn's default pairing and the icon set's naming is consistent. Runner up: heroicons, which would fight the shadcn examples in every doc page.
- **Theme provider**: `next-themes`. It handles system preference, persistence, and a small script on load that stops the wrong theme from flashing before React mounts; shadcn's own docs use it. Runner up: a hand rolled React context, which reimplements all three for no gain.
- **Class merging**: the standard shadcn `cn` helper (`clsx` plus `tailwind-merge`), so conditional classes compose without specificity fights. Runner up: template literals, which break the moment two utilities target the same property.
- **Form validation**: Zod major version 4 on the client, matching `backend/package.json`, with `@hookform/resolvers` pinned to a release that supports Zod 4 (older resolvers only accept Zod 3 schemas and fail at the type level). Runner up: Zod 3, which would force a version split when shared schemas arrive.
- **Accent color**: terracotta, sitting in the same warm band as the neutrals, used for links, focus rings, and the primary interactive accent. Separate values per theme, because one value cannot serve both. Light keeps `oklch(0.5442 0.1197 39.3)` (#A95437) with white text on it, verified at 5.24 to 1. Dark lifts to `oklch(0.6683 0.1447 51)` (#D97736) with ink text on it, verified at 5.83 to 1, and that lifted value used as link text clears 5.03 to 1 against the lightest dark surface. The light value cannot simply be reused in dark: as text on a dark surface it reaches only 3.52 to 1, and it cannot be lightened far enough to fix that while still carrying white text, so the two themes diverge on purpose. Wired as the `--primary`, `--link`, and `--ring` tokens rather than a single literal. Runner up: keeping the cool blue accent, which was already measured and would have cost nothing, but it fights every surface now that the neutrals are warm.
- **Neutral temperature**: warm tinted greys at a hue between 80 and 115, with chroma above zero on every neutral token, rather than stock zinc at near zero chroma (basis: the engineer's pick of the Ember palette against the running app, which replaced the cool tint this spec previously required). Light neutrals sit near hue 106 and dark neutrals near hue 90, both inside the band, with chroma between 0.0013 and 0.004. Text and surface greys that read as pure, for example `--foreground` and the dark surfaces, carry a chroma of 0.004 at their own hue rather than zero, which is what keeps them inside the scale. Runner up: the cool tint at hue 250 to 265 this spec recorded before, which is coherent on its own but now contradicts every surface in the code.
- **Surface ladder**: four distinct lightness values per theme in ascending order, `--background` then `--sidebar` then `--card` then `--popover`, so a card separates from the page by its own surface. This matters most in light mode, where the shipped tokens had `--card` and `--background` both at pure white, leaving a card defined only by its border. In light mode the ladder is #F6F6F5, #FAFAF9, #FDFDFC, #FFFFFF; in dark mode it is #151412, #181715, #1D1C1A, #222222. The light steps are small on purpose, because the palette wants every surface near white, so the ladder does the separating and the shadow in AC-13 does the rest. Runner up: a two step page and card ladder, which is simpler but leaves dialogs and dropdowns needing a border to float.
- **Border split**: `--input` (and `--sidebar-border`) hold 3 to 1 as the boundary of an interactive control, while `--border` drops to a decorative hairline that is not held to any ratio. Verified against the worst case surface in each theme: light input #878785 at 3.32 to 1, dark input #737370 at 3.35 to 1, light sidebar border #90908D at 3.05 to 1, dark sidebar border #80807E at 4.54 to 1. The decorative divider lands at 1.35 to 1 in light and 1.62 to 1 in dark, which is the intended hairline weight. Note that `--sidebar-border` is only structural in this codebase (it draws the panel edge, the group rule, and the floating sidebar ring), so a reading of criterion 1.4.11 could move it to the decorative set and leave it at a hairline; it is held to 3 to 1 anyway because AC-9 names it, and holding it is the conservative choice. Runner up: moving `--sidebar-border` to the decorative set, which is the stricter reading of the standard and would keep the sidebar edge light, but it narrows the bar AC-9 sets without evidence that the bar was wrong.
- **Elevation**: shadows carry depth in light mode and the surface ladder carries it in dark mode. Cards get a soft two stop shadow, dialogs and dropdowns a stronger one, and dark mode drops shadows to near zero. Runner up: shadows in both themes, which is simpler to implement but renders as a smudge on a dark surface.
- **Hover and selection surfaces**: `--accent` picks up a tint of the primary hue so hovered and selected rows are legible as such, and `--secondary` and `--muted` become distinct values rather than sharing one. In light mode the three are #F2F2F1 (secondary), #F5F5F4 (muted), and #F5EFEA (accent); in dark mode they are #2D2C2A, #232220, and #3F342F. Before this revision all three collapsed onto one value per theme, so a hover state was invisible. Runner up: keeping all three neutral at three lightnesses, which is quieter but leaves selected navigation rows relying on weight alone.
- **Focus ring rendering**: the `--ring` token is an opaque color at full strength, not shadcn's default partial opacity ring, because a faded ring fails the 3 to 1 non text contrast bar. Runner up: keeping the default ring and accepting the accessibility debt, which contradicts AC-9.
- **Shell composition**: shadcn's Sidebar component (it already handles collapse, mobile drawer behavior, and keyboard support) composed with Card, Button, and the other Slice 1 pieces, rather than a hand rolled flex layout. Note: the Sidebar persists its collapsed state in a `sidebar_state` cookie, which is a harmless UI preference, not an auth cookie, and must be handled correctly when feature 4 introduces real session cookies. Runner up: a custom layout plus Sheet for mobile, which reimplements the accessibility work the component already ships.
- **Theme toggle shape**: a three way toggle (light, dark, system). A two way switch makes the system preference unrecoverable once the user has chosen, which quietly breaks the "respect the system" behavior after one click. Runner up: a two way light and dark switch, simpler but lossy.
- **Font pairing**: Newsreader for headings and Inter for interface text, with Geist Mono kept for code snippets only. Newsreader is what makes the shell read as a product rather than a tool: h1 to h3 take `font-heading`, which `globals.css` resolves to `--font-newsreader`, while h4 and everything below stay in Inter. The layout must expose all three variables through `next/font` (`--font-inter`, `--font-newsreader`, `--font-geist-mono`), because `globals.css` names them and a missing one falls back silently instead of failing. Inter's tabular figures are opt in: design.md documents that numeric columns should use the `tabular-nums` utility, since the default proportional figures drift in dense tables. Runner up: Inter alone, which is what shipped first and costs nothing extra, but it leaves headings indistinguishable from body text.
- **Nav config**: one typed module (label, href, lucide icon, optional `disabled` flag) seeded with the planned sections (dashboard, schedule, tasks, contacts, follow ups, briefing). Items for sections not yet built render as disabled list items, not links, so the accessible navigation never points at a 404. Runner up: seeding only live routes, which leaves the shell looking empty and pushes the nav shape decision into a later feature.
- **Search in the top bar**: a visual slot only (a styled input or button that does nothing). Search behavior belongs to feature 12.
- **User menu in the top bar**: a placeholder until auth (feature 4) provides the session. The shell must not assume a logged in user yet.
- **UI design guidance**: the `frontend-design` skill (`anthropics/skills`, `.agents/skills/frontend-design/`) is the art direction standard for any UI work in this project. An agent building a screen loads it alongside the shadcn and Tailwind skills, and root `AGENTS.md` lists it so that happens without being asked. It governs the process rather than the values: ground the work in the subject, plan and review before writing code, spend the boldness in one place, and write interface copy from the user's side. Its palette instincts do not apply, because Ember is the pinned brief and a pinned brief wins under the skill's own rules. Vendored into the repo rather than pointed at a home directory path, so a fresh clone and CI see the same guidance as this machine, and so the path convention matches the49 skills already listed. Runner up: no named skill, which leaves each agent inventing a visual approach per screen and reproducing exactly the templated defaults the skill exists to avoid.

## Feature design

**Data model sketch**:
No database entities and no migration; this feature touches no schema. The persistent artifacts are code and CSS:

- Token layer: CSS variables in `client/app/globals.css` wired through Tailwind 4 `@theme`, following the shadcn semantic naming (background, foreground, card, muted, border, input, ring, primary, and the chart and sidebar families shadcn generates). Light values on `:root`, dark values under the `.dark` selector, written as `oklch()` with the source hex kept as a trailing comment so a reviewer can read either form. Every neutral carries chroma above zero at a hue between 80 and 115. Four lightness steps per theme: `--background`, `--sidebar`, `--card`, `--popover`, ascending. `--input` and `--sidebar-border` are set to clear 3 to 1 against the worst case surface in their theme; `--border` is a decorative hairline and is deliberately below that bar. Headings resolve through `--font-heading: var(--font-newsreader)`, which the layout must provide.
- Nav config: a typed module (for example `client/lib/nav.ts`) exporting an array of `{ label, href, icon, disabled? }` items; `disabled` renders a non interactive row. No database backing; edits are code changes.
- Design doc: `client/design.md`, with token tables generated from `globals.css` by a small script or a documented copy step so the doc cannot silently drift from the code.

**State transitions** (theme only; no domain state machine):
theme: `system` (default on first visit) → user picks `light`, `dark`, or `system` on the three way toggle → choice persisted by next-themes (localStorage), read again on next load. Selecting `system` hands control back to the OS preference and stays live if the OS preference changes.

**API surface**:
None. This feature is client only and adds no endpoints. Later features own their own surfaces.

**Value sourcing** (every value the acceptance criteria display names where it comes from):

| Action | Value produced / displayed | Source |
|---|---|---|
| Render any screen | Colors, spacing, radii, fonts | CSS variables in `globals.css` via `@theme`; semantic token utilities only; warm tinted neutrals, four step ladder, and per theme accent and border values set in the token layer |
| Render a heading | Which typeface it uses | `--font-heading` in `globals.css`, resolved to `--font-newsreader`, which the layout declares with `next/font`; h4 and below stay on `--font-sans` |
| Render a card or panel | Which surface level it sits on | Its surface token: `--background` for the page, `--card` for a card, `--popover` for a floating layer; never a raw color |
| Render a hovered or selected row | Its surface color | `--accent` (primary tinted) for hover and selection, `--secondary` and `--muted` for the neutral surfaces |
| Render a control boundary | Its outline color | `--input` (or `--sidebar-border` in the nav), held to 3 to 1; decorative dividers use `--border` and are not held to any ratio |
| Render the sidebar nav | Section labels, hrefs, icons, disabled state | Typed nav config module in `client/lib/` (seeded with planned sections; unbuilt sections carry `disabled: true`) |
| Toggle theme | Current theme name (light, dark, or system) | next-themes state (localStorage under its default key) |
| Demo form validation messages | Error text | Zod schema messages defined next to the form schema in client code |
| Contrast verification | Measured ratios | Computed from the token values at verify time (AC-9); measured against the worst case surface in each theme, not against white; no runtime feature |

**Key invariants**:
- Application code never hardcodes a color, font size, or radius; it uses semantic token utilities or the type scale tokens defined in `globals.css`. Raw palette utilities (for example `bg-zinc-100`) appear only inside the token layer itself.
- The 3 to 1 non text contrast bar applies to interactive component boundaries and the focus ring only. Decorative borders use `--border` and are exempt. Any future component that draws a control outline must take it from `--input` or another token in the interactive set, never from `--border`.
- Every neutral token in the surface ladder and the emphasis set carries chroma above zero at a hue between 80 and 115. A pure grey at chroma zero does not belong in the scale, in either theme.
- Every interactive component shows a visible focus indicator at full opacity, is fully keyboard operable, and meets the minimum target size; this is inherited from shadcn where it holds, and enforced by token overrides plus the automated check where stock shadcn falls short.
- The root layout stays a server component; only leaf interactive pieces (theme toggle, sidebar collapse trigger, form fields) opt into the client boundary. The `<html>` element carries `suppressHydrationWarning` so next-themes' class injection does not trip hydration, and the theme toggle renders a stable placeholder until mounted for the same reason.
- The shell does not read a session or assume an authenticated user; auth wiring is feature 4.
- New UI starts from `client/design.md` and the `frontend-design` skill, never from a fresh aesthetic idea. The skill's process applies; its default palette does not. Ember, the type pairing, the surface ladder, and the token utilities in `globals.css` are decided here and are not reopened per screen.

**Security model**:
No auth, no protected data, no meaningful new attack surface. The shell's user menu is inert until feature 4. One honest exception: shadcn's Sidebar persists its collapsed or expanded state in a `sidebar_state` cookie. That cookie holds a UI preference only (no identity, no authorization), but it is a cookie, and feature 4's session cookie review should see it rather than be surprised by it. Nothing else about this feature touches the backend, cookies of consequence, or tokens. When auth lands, route protection and role aware navigation become that feature's job; this spec only requires that the nav config be easy to filter by role later (a plain array with an optional `disabled` flag makes that a trivial `.filter`).

**Configuration required**:
None. No new environment variables, secrets, or third party accounts. Theme persistence is client side storage. Fonts load from Google via `next/font` (already the scaffold pattern); if a future deployment constraint forbids Google Fonts, swapping the loader is a localized change in the layout.

**Critical test scenarios** (each maps to an acceptance criterion in Requirements):
- Happy path: open the app, see the shell with sidebar and top bar, set the theme to each of light, dark, and system, navigate sections with the keyboard, reload and confirm the choice persisted, verifies **AC-5**, **AC-6**
- Keyboard and focus: tab through the shell and open the dialog component; focus is trapped while open, Escape closes it, and focus returns to the trigger; every tab stop shows a visible full opacity ring; tabbing never lands on content hidden under the sticky top bar, verifies **AC-4**
- Target size: measure the icon only top bar controls (theme toggle, any icon button) against the 24 by 24 CSS pixel minimum, verifies **AC-4**
- Contrast: measure body text, secondary text, link text, input borders, and the focus ring in both themes against the AA thresholds (4.5 to 1 text, 3 to 1 interactive boundaries), measuring each against the worst case surface in its theme rather than against white, verifies **AC-9**
- Surface ladder: in each theme confirm `--background`, `--sidebar`, `--card`, and `--popover` resolve to four distinct lightness values in ascending order, and that a card is distinguishable from the page with its border removed, verifies **AC-11**
- Hover and selection: hover a dropdown row and select a navigation item; both change to a surface that is visibly different from the resting surface, and `--secondary` differs from `--muted`, verifies **AC-12**
- Elevation by theme: in light mode a card carries a shadow and a dialog carries a stronger one; in dark mode both rely on the surface ladder and carry no visible shadow, verifies **AC-13**
- Neutral chroma: read every neutral token in both themes and confirm chroma is above zero at a hue between 80 and 115, verifies **AC-14**
- Automated accessibility: run axe (via Playwright or the test runner) against the demo views in both themes; zero serious or critical violations, verifies **AC-4**, **AC-9**
- Form errors: submit the demo form empty or invalid; errors render inline, focus moves to the first invalid field, and the error is programmatically associated with the input, verifies **AC-7**
- State patterns: drive the demo view through loading, empty, and error; each renders the shared pattern rather than a one off, verifies **AC-8**
- Typecheck gate: `client/` passes lint, format, and typecheck, verifies **AC-10**, **AC-3**

## Build approach

Tracer Bullet, per the project default recorded in the scope header. The first milestone is a thin vertical thread: shadcn initialized, tokens live, Inter swapped in, next-themes wired, and one page rendering inside a minimal shell with a working theme toggle. That proves the whole path end to end. Later milestones thicken one segment at a time: the full component set, the real shell, states and forms, then design.md and the accessibility pass. No milestone fakes data; there is no data yet, which is fine for a foundation feature.

## Consequences

**Positive**:
- Every later feature starts from a real frame and real tokens; screens compose instead of inventing chrome.
- Accessibility (focus, keyboard, contrast) is paid for once, in the components, rather than per feature.
- The dark theme, the form engine, and the state patterns arrive before the first product screen needs them, which removes the usual blockers that appear halfway through building a slice.
- design.md gives humans and later agents one place to check the visual contract.

**Negative / tradeoffs**:
- The shell ships before auth, so the user menu is inert and some nav items may 404 until their features land; anyone clicking around early sees rough edges that are not bugs.
- Owning copied shadcn source means occasional manual merges when upstream components improve; there is no automatic `npm update` for UI.
- Inter and Newsreader are external font dependencies (both loaded from Google via `next/font`); a deployment that blocks Google Fonts needs a local font swap for two families instead of one.
- Meeting the interactive boundary bar still means overriding shadcn's stock zinc `--input` and `--ring` values, and this revision adds a third visible departure: decorative borders are lighter than stock shadcn, the neutrals are warm tinted rather than pure, and `--sidebar-border` at 3 to 1 is a noticeably firmer line than the hairline `--border` beside it. Anyone comparing against a default shadcn app will see the difference on the first screen.
- The warm palette has less contrast margin than the cool one did. Light `--muted-foreground` clears 4.5 to 1 by 0.15 and light `--sidebar-border` clears 3 to 1 by 0.05, so either token is one small edit away from failing again, and a future darkening of `--muted` or lightening of the sidebar will break it.
- The `frontend-design` skill's calibration section names a warm cream ground, a high contrast serif display, and a terracotta accent as the first tell of AI generated design, which is close to this palette. Its own rule is that a pinned brief wins, so Ember stands, but an agent that loads the skill is handed a reason to question a direction this spec already settled, and it needs this spec to say why it does not.

**Neutral**:
- The `new-york` style sets a specific radius and border treatment; changing it later is a global restyle, so it is worth being deliberate now (it was).
- The nav config becomes a file every section feature will touch; that is intentional and cheap, but it is a shared file to keep merge friendly.
- No Storybook: component documentation lives in design.md and in the components' own source. If the component count grows past what one doc holds, revisiting that is a reasonable follow-up.

## Migration plan

**Strategy**: no migration needed
**Phases**:
1. Replace the token values in `globals.css` with the Ember values and wire the light mode shadows into Card, Dialog, and DropdownMenu. No schema, no data, no coordination window.
2. Declare Newsreader in the layout, restore the sidebar trigger in the top bar, rewrite the `design.md` prose, then regenerate its token tables and run the contrast and accessibility gates.
**Rollback**: revert the commit. The change touches CSS variables, one font declaration, one component line, and a doc, so one commit restores the previous look in full.
**Risks**: the retuned values shift every screen at once, so any screen that quietly compensated for the old values (by relying on a heavy border for separation, or on white text over a dark accent) will need its own check. Two tokens sit within 0.05 and 0.15 of their bars, so a later palette edit can break the gate without an obvious cause. Nothing here is irreversible and nothing is behind a flag, since the blast radius is visual and the revert is one commit.
